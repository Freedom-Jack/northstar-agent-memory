**Lessons.**
- **Product goals are completion contracts**, a finish line judged met or not met. Claude Code judges it with a fresh evaluator; Codex lets the model self-assess. None holds an aspiration above the activity ("succeed in the interview"), and none judges "still improving" or "peaked". [E]
- **No product suggests a fresh session for quality reasons on its own.** Every unprompted "start new" is about cost or capacity: the Claude Code resume dialog, claude.ai usage advice, ChatGPT's hard limit. Quality-driven restarts appear only as user best practice. [E] This matches the probe: the session's own AI never offered one.
- **The fresh-session move is user-invoked and carries a goal.** Amp drafts a new thread from a stated goal plus files. Devin carries the diff and findings. Claude Code takes compaction instructions, summarizes from a chosen turn, or branches. [E]
- **Side errands get their own lane:** Cursor side chats, Claude Code `/btw`, Amp's one thread per task, and Claude Code's "kitchen sink session" anti-pattern. [E]
- **Degradation detection is mechanical only:** token thresholds, Gemini loop detection, the `/goal` stall stop. [E]
- **There is a hook at the return from a break:** the Claude Code session recap. [E]

## 2. What research says

| # | Finding | Source |
|---|---|---|
| 2.1 | Once a model takes a wrong turn it "does not recover". The paper's advice to users: "starting a new conversation that repeats the same information" may do much better, and consolidate first. Recap and snowball only partly mitigate. | Laban et al., arXiv 2505.06120, §7.1 and §7.4 [E] |
| 2.2 | Every model drifts from its goal, and drift tracks "susceptibility to pattern-matching" as context grows. The best scaffolded agent held for more than 100k tokens. | Arike et al., arXiv 2505.02709 [E] |
| 2.3 | Persona drift: "no evidence that adaptive timing outperformed static scheduling". Monitoring is "more useful for deciding what to correct than when". A monitor-written, behaviour-specific instruction cut drift 87%. | Leins et al., arXiv 2609.24532 [E] |
| 2.4 | Models "know but violate" constraints; checkpointing "does not close the dissociation". Length alone hurts (context rot). | DriftBench, arXiv 2604.28031 [E]; note 11 §3 |
| 2.5 | Predicting **when** to offer help is hard even with training: the best fine-tuned model reached F1 0.66. | Lu et al., ICLR 2025, arXiv 2410.12361 [E] |
| 2.6 | I found no work that detects in real time when a user should restart, and no study of when people choose to. | Searches, 2026-10-23 (absence is unverified) |
| 2.7 | Search sessions: time gaps alone cap at about 70-80% precision for task boundaries, and the 30-minute standard "receives no support". Time does better on coarse "missions" than on fine goals. Word overlap beat time (goal boundaries 89% vs 62.5%). 17% of tasks are interleaved. | Jones & Klinkner, CIKM 2008, dmice.ohsu.edu/bedricks/courses/cs606-ir/papers/jones_2008.pdf [E] |
| 2.8 | Deferring notifications to breakpoints reduced frustration and reaction time; coarser breakpoints cost less. Content relevant to the task suits fine or medium breakpoints, general-interest content only coarse ones. Relevant content raised tolerance (frustration 3.59 vs 4.98). | Iqbal & Bailey, CHI 2008, interruptions.net/literature/Iqbal-CHI08.pdf [E] |
| 2.9 | Interrupting at the best predicted moments (between subtasks) produced 56% less annoyance and 43% more "respect" than the worst moments. | Adamczyk & Bailey, CHI 2004, hci.rwth-aachen.de/materials/conferences/CHI2004/1p271.pdf [E] |
| 2.10 | Mixed initiative: the threshold for acting rises with the user's depth of focus. **Asking** has its own lower threshold than acting. Provide efficient invocation and termination, minimize the cost of poor guesses, and "continue to learn by observing". | Horvitz, CHI 1999, erichorvitz.com/chi99horvitz.pdf [E] |
| 2.11 | Proactive coding assistant (n=65): 90% preferred the moderate variant, but only 47% the more frequent "Persistent" one ("distracting and annoying"). Relevance was the main complaint. Participants asked for "an opt-in feature" or adjustable frequency. | Chen et al., CHI 2025, arXiv 2410.04596 [E] |
| 2.12 | Proactive agents raised efficiency but disrupted workflow. Presence indicators and shown context reduced the disruption (n=18). | Pu et al., CHI 2025, arXiv 2502.18658 [E, abstract only] |
| 2.13 | False alarms: about 90% of people match their response rate to an alarm's reliability. Acceptance of clinical reminders fell 30% for each extra reminder per encounter, and 10% per 5-point rise in repeats, with no decline over time for a new alert. | Bliss et al., *Ergonomics* 1995, stars.library.ucf.edu/scopus1990/1980 [E, abstract]; Ancker et al., *BMC MIDM* 2017, pmc.ncbi.nlm.nih.gov/articles/PMC5387195 [E] |
| 2.14 | False-alarm-prone automation hurts both compliance and reliance; miss-prone automation hurts compliance only. | Dixon, Wickens & McCarley, *Human Factors* 2007 (unverified, secondary) |

## 3. Implications for Northstar's focus job

1. **[L] Stop trying to infer the moment from the session alone; the probe agrees with the literature.** Nobody has shown it. Trained proactive agents reach F1 0.66 (2.5), monitors help with *what* more than *when* (2.3), and time alone caps at 70-80% (2.7). The probe's AUC 0.52-0.58 fits this. Content features beat time in search logs (2.7), but there the content is topic change. The user's marks rest on their own judgment of quality and fit, which the session doesn't show.
2. **[L] Time the remarks to coarse breakpoints: a return after a break, and the end of a phase.** Coarse breakpoints cost least (2.8, 2.9). A meta suggestion like "start fresh" is general-interest content, which belongs only at coarse points (2.8). The new-day signal (5 of 13 marks, 1 false alarm) is a coarse "mission" signal, where time works best (2.7). A product hook already exists: the Claude Code session recap on return (§1).
3. **[L] Rate matters more than cleverness.** Frequency halved preference (90% to 47%, 2.11). Each extra reminder cut acceptance 30%, and repeats did more harm (2.13). People discount a source to its hit rate (2.13). So: at most one unprompted remark per coarse breakpoint, never repeat a suggestion the user declined, and miss rather than nag (2.14, unverified). The new-day rule's precision (about 5 in 6) is high enough that remarks would likely stay read.
4. **[L] Firmness is a Horvitz threshold.** Each setting shifts the threshold for speaking (2.10): silent; a passive goal line; a check offered at breaks; a suggestion with a drafted handoff. "Ask" sits below "act", and focus never acts on its own (no auto-new-session, no rewritten answers; GOAL §2). Dismissing a remark takes one word, and the dismissals are logged as the user's feedback, which fits the probe's reading that the marks encode a per-user working style (2.10, factor 12).
5. **[L] Make "start fresh with the goal and the best version" one move the user can invoke at any time.** This is what users did in both probe sessions, and what Amp, Devin and Claude Code offer (§1). Seed the new session from consolidated state, not the drifted transcript (2.1; note 11 §2). Northstar adds two things no product carries: **the goal above the activity**, and **the best version the user chose**. Product checkpoints are per turn and cover code only. The watchers picked the newest version, not the best, so the handoff should ask the user to confirm which version is best.
6. **[L] For side topics, offer a side lane rather than a warning.** Interleaved tasks are normal (17%, 2.7). Products park tangents in side chats or `/btw` (§1). A one-line offer to split or park a side topic is task-relevant, so it can come at a medium breakpoint (2.8). It should still count toward the rate budget in item 3.
7. **[L] Hold the goal visibly but quietly.** Product goals are finish lines a judge checks every turn. An aspiration like "succeed in the interview" can't be checked that way. A persistent goal line, like Codex's progress row or Claude Code's `◎ /goal active` indicator, keeps it in view without speaking, and presence cues reduce disruption (2.12).
8. **[L] Use the user's own feedback as a cheap trigger for a check, not as a verdict.** Claude Code's "corrected more than twice on the same issue" rule (§1), and the user's cues ("Looks like you start breaking things now"), are signals in the user's turns. Test whether they line up with the user's marks before using them. Untested.

## 4. Open questions

- Does a single check at a return after a break help on held-out sessions, and how many unhelpful remarks will the user tolerate before ignoring them? (2.13 predicts a fall-off.)
- Does "corrected twice" or explicit dissatisfaction coincide with the user's marks? This can be checked against existing marks without new probe runs.
- On claude.ai and ChatGPT web there are no hooks. Can the extension detect breaks and phase ends reliably from timestamps alone?
- How should a best version be stored when it isn't code (screenshots, a deployed page)? Should the user always pick it, or confirm one of two candidates?
- Does a passive goal line count as "speaking up"? This is a question for the user, since it touches "speaks up rarely".
